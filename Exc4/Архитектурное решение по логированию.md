# 4. Архитектурное решение по логированию

Сбор логов необходим со следующих компонент:

- shop api
- crm api
- mes api
- rabbitmq

Логируем изменение статуса заказа:

- Время события
- Идентификатор заказчика
- Идентификатор заказа
- Текущей статус заказа
- Выполняемое над заказом действие
- Название компоненты и его инстанса порадившей лог

Лог должен генерироваться перед началом действия с заказом и по завершению этого действия

В случае если выполнить действие не удалось необходимо генерировать лог уровня ERROR


## Мотивация

- Сокращения времени реакции на проблемы
- Осведомленность о состоянии системы вне зависимости от реакции пользователей
- Появление инструмента для выявления сложных (логических) ошибок системы

В первую очередь нужно реализовать логирование создания заказа и завершения заказа

## Предлагаемое решение
- Создание ELK стека (OpenSearch, Logstash, Kibana)
- Подключение компонент к ELK (установка Beats)
- Доработка компонент для отправи логов
- Настройка анализа логов для выявления проблем и проведения оповещения административного персонала

## Безопасность
Доступ к логам предоставляется только для административного персанала, аутантификация обеспечивается встроенными средствами Kibana.
Маскирование чувствительной информации перед отправкой в ELK обеспечивается средствами Beats
Логи каждого компонента будут хранится в отделных индексах.
Храниние логов необходими в течение 3 мес.
Необходимо обеспечить оповещение администраторов:

- если количество ERROR сообщений превышает 10% от INFO сообщений.
- если скорость поступления логов выросла на 300% за минуту
